# Canvas

Canvas is Tringify's reference storefront theme: clean, white and product-first. It is the theme new stores start with and the starting point for your own theme. Fork it, rename it and make it yours.

What's included:

- 70 sections covering every storefront page: home-page sections, product, listings, search, cart and cart drawer, account, sign-in, blog, gift cards, wishlist, the gate pages (coming soon, password, maintenance) and the overlays (cookie banner, age gate, country prompt, popups).
- 20 theme blocks for section content (headings, text, buttons, images, slides, tiles, footer columns).
- Three header layouts and three footer layouts, swappable in the editor.
- Three style presets: **Everyday**, **Editorial** and **Night**.
- Storefront text in ten languages (en, de, es, fr, it, ar, he, hi, th, zh-TW) and editor labels in five (en, de, es, fr, it).
- A demo catalog for local previews.

## Requirements

- The [Tringify CLI](https://github.com/tringify/cli). It downloads the theme tools it needs on first use.
- Python 3, for `scripts/sync_partials.py`.

## Quick start

```sh
tringify login
tringify theme init my-theme
cd my-theme
tringify theme preview
```

`init` copies Canvas into `my-theme`, sets the theme's name, builds the sections and validates the result. `preview` serves the theme locally with the demo catalog and rebuilds when you save.

To start from a clone of this repository instead:

```sh
git clone https://github.com/tringify/canvas.git
tringify theme init my-theme --from canvas
```

Work against a development store, then check the theme before you publish:

```sh
tringify login --store
tringify theme dev --store STORE_ID --with-demo
tringify theme check
```

`theme dev` syncs every saved change into an unpublished theme on the store; the store's published theme is never changed. `--with-demo` also adds the demo products and collections (development stores only). `theme check` validates the theme with the same rules used on upload (`--mode sealed`, the default).

`scripts/check.sh` runs the full local check in one go: it syncs the partials, builds the sections and runs `tringify theme check`. To write an upload-ready ZIP, run `tringify theme package . dist/my-theme.zip`.

See [Theme development](https://dev-docs.tringify.com/themes/) for the full guide.

## Project structure

```
src/
  sections/<name>/       Section source: body.html, style.css, schema.json
  _shared.css            Design system, prepended to every section by the build
  .generated-sections.json  Build index of generated sections (keep it in version control)
sections/*.vasc          Compiled sections (generated by `tringify theme build`; do not edit)
blocks/*.vasc            Theme blocks (edited directly)
partials/                Markup, CSS and scripts shared by several sections and blocks
templates/               Page templates, style templates (templates/styles/) and global surfaces
config/                  Theme settings schema and style presets (config/presets/)
locales/                 Storefront text (<lang>.json) and editor labels (<lang>.schema.json)
assets/                  Default photos and layout preview images
demo/                    Demo catalog and images for local previews
scripts/                 sync_partials.py and check.sh
theme.json               Theme manifest: name, version, sections and surfaces
tokens.json              Default colour tokens
```

## Working on the source

### Sections

Each section lives in `src/sections/<name>/` as `body.html` (markup), `style.css` and `schema.json`. `tringify theme build` compiles them into `sections/<name>.vasc` and updates the section list in `theme.json`. Edit the sources, never the compiled `.vasc` files. A section declares the data it reads in `ctx_needs`.

`src/_shared.css` is the design system: colour schemes, type scale, buttons, fields, focus, notices and the spacing scale. The build prepends it to every section, because each section is standalone.

### Partials

Markup, CSS and scripts shared by several sections live in `partials/`: the product card, cart parts, filters, the sign-in and address forms, the phone field, the country and language picker, and the header and footer building blocks. A section or block marks where a partial goes:

```
{%- comment -%}partial:card{%- endcomment -%} … {%- comment -%}/partial:card{%- endcomment -%}
/* partial:facets */ … /* /partial:facets */
```

`python3 scripts/sync_partials.py` copies each partial between its markers. Run it before building; `--check` exits non-zero when a section is out of date. A partial can mark places for other partials (the phone field sits inside the sign-in and address partials), and the sync fills both. Some partials read a variable that each place must set on the line before the marker (for example `cv_wl` before `partial:card`); the sync script reports a place that forgets. Change shared parts in `partials/` and sync, never in one section's copy.

### Theme blocks

Section copy lives in theme blocks (`blocks/<name>.vasc`), not in fixed settings.

- **Content blocks**: `eyebrow`, `heading` (optional link), `text` (rich text), `buttons` (up to two), `image` and `spacer` (optional divider). Their "Section's style" size takes the look the section gives that part (`.cv-blk-*--auto`, styled in each section's CSS); the other sizes use the theme's scale.
- **Containers** hold content blocks: `slide` (slideshow), `promo-tile` (promo grid), `split-tile` (split promo), `column` (multicolumn) and `mega-promo` (header mega menu promotions). Rich text, image with text, newsletter, contact form and video take content blocks directly.
- **Footer blocks**: `footer-column`, `menu-links`, `newsletter-form`, `social-links`, `contact-details`, `payment-methods` and `logo`.
- **Other blocks**: `cart-recommendations` (Recently viewed, for the cart page and the cart drawer) and `discount-code` (a code with Reveal and Copy, for popups).

Each slot names the blocks it accepts in `blocks.theme_blocks`, so a slideshow offers only slides and a slide only content blocks. A container keeps what its layout owns (image, theme photo, link of the whole tile). The section works out the theme photo for a container's place and passes it as `--cv-fb`. A linked tile is a pointer target over the whole tile (`.cv-tile-link`); its heading and button blocks carry the same link for keyboards and screen readers.

### Templates, presets and surfaces

`templates/*.json` are the page templates. `templates/styles/<preset>/` holds the templates each style preset brings, and `config/presets/` holds the presets' settings. The header and footer are global surfaces (`templates/global_body_start.json`, `templates/global_body_end.json`). The alternative layouts are swappable through `required_one_of` groups in `theme.json`, and each layout has a `preview_image` in `assets/canvas-layout-*.png` (600×340) for the editor's layout picker.

### Text and translations

Shopper-facing text is in `locales/<lang>.json` and editor labels in `locales/<lang>.schema.json`, with flat dotted keys. Schema defaults point at storefront text with `@t:<key>`, so seeded copy appears in each shopper's language. The theme check requires every editor label in all five editor languages. When you add a key, add it to every locale file.

### Schema migrations

Section and block schemas carry `migrations` (`rename_block`, `settings_to_blocks`, `rename_setting`, `remove_setting`). They convert settings saved by earlier versions of Canvas when a store updates. Keep them when you change a schema, and never read the old settings in markup.

## Conventions

- **Print the platform's words.** Prices go through `money`. Tax, shipping and duty notes, offers, stock reasons, gift card statuses and error messages are printed as the platform gives them, in the shopper's language. The theme never calculates with money values or rewords platform text.
- **Shopper actions use the documented forms** (`cart_add`, `cart_update`, `wishlist_toggle`, `localization_set`, `shopping_mode_set`, …). Every form works without JavaScript as a plain POST; with JavaScript, the platform bridge updates the page in place.
- **Nothing invented on the live store.** Sections without the merchant's content hide on the live store and explain themselves in the editor. Placeholder art, sample videos and sample cards show in the editor only.
- **Accessibility.** Focus rings show for keyboard use only (see the focus rules in `src/_shared.css`). Drawers, sheets and dialogs trap focus and close on Escape, and phone tap targets are at least 44px.
- **Overlays in the editor.** Every overlay that starts hidden opens on `tf:section-selected` for its own section and closes on `tf:section-deselected`. In the editor it opens nothing by itself and stores nothing.

## Feature reference

### Header and footer

Three header sections (`header`, `header-split`, `header-mega`) and three footer sections (`footer`, `footer-wordmark`, `footer-compact`) render the same store data and behave the same; only layout and styling differ. They share their parts through `partials/header-*` and `partials/footer-*`: theme-wide variables, the skip link, icons and counts, search, the menu sheet, the header script and the footer's columns, bottom bar and fold script. The header script also runs the theme's card picker, button feedback and form notices, so every header must include it.

Each header names itself in `data-cv-type` and in `cv_refresh`, the key the platform uses to refresh the cart and wishlist counts after an action.

The footer is made of theme blocks plus its own bottom-bar blocks: `copyright` (`{year}` and `{store}` are filled in), `policies` (policy links and the cookie preferences link), `localization`, `social`, `payment`, `note` and `powered_by`. Merchants show, hide and order them. Footer columns can fold behind their headings on phones.

### Navigation

Header and mobile navigation render up to three menu levels; footer menu blocks render top-level items only. Every placement supports items without a link (rendered as labels) and links that open in a new tab. Read the selected menu from `settings.menu_resolved` (or `b.settings.menu_resolved` in a block); `ctx.menus` holds summaries, not trees. Leave out "View all" when a parent has no destination.

### Country and language picker

`partials/loc-picker.html` (with `loc-picker.css` and `loc-script.html`) is the one picker used by the header, the footer bar and the country prompt. Styles: dropdown (native selects), compact pill, flags with names in a centred dialog, a side sheet with search, and inline text links. Every list is a bottom sheet on phones. Theme settings › Country and language set the default style, flags, currency display and language names or codes; each placement can override the style. Everything comes from `ctx.localization`, and every choice posts `localization_set`. Lists over ten entries get a search. Without JavaScript the list styles become a `<details>` disclosure.

### Product page

- **Blocks** for every part of the buy box, including price notes (the market's tax, shipping and duty notes from `product.price_notes`), available offers (`product.offers`, printed as given), stock counts, breadcrumbs, the vendor link, express checkout (`ctx.express.slot`) and the platform metafield block (`theme:metafield`).
- **Gallery layouts**: classic, stacked, thumbnails rail, wide carousel and focus. Phones always get a swipe gallery.
- **3D models** load `<model-viewer>` from jsDelivr, pinned with an SRI hash in `main-product`, only when a model slide nears the screen. To change the version, update the URL and the `sha384-` hash together.
- **Sticky add to cart**: a bar that shows while the Buy buttons block is out of view, with optional variant picking (inline values or a sheet), quantity and a wishlist heart. It holds no form of its own: it drives the block's form, so the cart, button feedback and express checkout all read one form.
- **Gift cards**: the recipient fields take every `maxlength` from `ctx.forms.cart_add`. The "Send on" picker posts the shopper's chosen moment as RFC 3339 with its offset. Cart lines print `deliver_at_display` as given, and the theme never formats the time.
- **Quick view** (`partials/quick-view.*`): Choose options on cards opens the product page's own buy box in a drawer, fetched with `?_sections=main-product`.

### Listings and search

- **Filters** (`partials/facets-*`): sidebar, filter bar or drawer layouts, and a bottom sheet on phones. Every choice is a link or GET form, so the state lives in the URL. Long value lists get a search and load the platform's further pages in place. Applied ranges print through `format_number` and the price through `money`.
- **Paging** (`partials/pager.html`): numbered pages, a Load more button or infinite scroll.
- **Predictive search**: one implementation (`partials/suggest-script.html`, `window.cvSuggest`) for the header and the search page, fetching `routes.search_suggest_url`.

### Cart

`main-cart` and `cart-drawer` are made of blocks in the merchant's order. Line items and app blocks (such as Recently viewed) render beside the summary (`partials/cart-main`). Free shipping progress, offers, discount codes, totals, price notes, the order limit notice, optional services, the shopper's note, the shipping estimate, checkout and express checkout render in the summary (`partials/cart-summary`). Checkout always shows, and stays disabled while the platform says the cart cannot check out (`cart.checkout_ready`). It names its reason with `aria-describedby`.

### Account

`main-account` covers orders (with refunds and order totals as the platform reports them), addresses (fields from `customer.address_form`, per country), gift cards received and sent, store credit, profile and email confirmation.

### Pickup

While the store offers pickup (`shopping.pickup_available`), the header shows a Delivery / Pickup chip that opens `partials/pickup-sheet.html`. Any `[data-cv-pk-open]` element opens it. Choices post `shopping_mode_set`, and the page reloads because every stock figure follows the mode. Without pickup nothing renders.

### Wishlist

`main-wishlist` uses the shop grid's card (`partials/card.html`) in wishlist mode, so Theme settings › Product cards apply. Saved variants show their own options, photo and price, and Move to cart adds them directly.

### Gate pages and overlays

- **Gate pages** (`main-coming-soon`, `main-password`, `main-maintenance`; shared parts in `partials/gate-*`) render without the header and footer, so they bring their own top row and footer. Every form is a plain POST without JavaScript. The maintenance page checks every 30 seconds whether the store is back.
- **Age gate**: rendered only while `ctx.age_gate.show` is true. The platform's runtime handles focus, remembering the answer and declining.
- **Cookie banner**, **country prompt** and **popups**: several layouts each. The platform decides when the banner and the prompt show. Popups remember they were seen in the browser's local or session storage, never in a cookie, and wait for the other overlays.
